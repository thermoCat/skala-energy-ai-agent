# 주유소 복합 에너지 허브 전환 Agent

SK에너지 서울 주유소 네트워크가 **어느 주유소에, 어떤 에너지를, 언제** 더할지 공공 실데이터로 판단하고, 그 뒤에도 매일·매주 변화를 추적하게 돕는 멀티 에이전트 서비스와 관리자 대시보드입니다.

- 대상: 서울 25개 자치구, 주유소 397곳 + LPG 충전소 73곳 (SK에너지 130곳)
- 연료: 휘발유 · 경유 · LPG · 전기 · 수소
- 원칙: **실데이터만** · **판별은 LLM, 검증과 최종권은 코드(권위 게이트)** · **결정은 사람**

## 무엇을 해결하나

| 사용자 | 문제 | 서비스가 하는 일 |
|---|---|---|
| 리테일 네트워크 관리자 | 수요가 지역마다·매달 바뀌고, 데이터가 5개 기관에 흩어져 있다. 설치한 충전기가 멈춰도 늦게 안다 | 지도 한 화면, 일간 추적(새로 멈춘 급속을 이유별로 알림 1건), 주유소 주간 추적 변화 보고 |
| 투자 검토 담당자 | 어느 주유소에 무엇을 넣을지 근거가 없다. 잘못 고르면 설비가 놀아 적자 | 자치구·묶음 진단, 급속 후보와 이유, "충전기 N대 신설하면?" 시나리오, 현장 확인 항목 |

## 어떻게 동작하나

```
질문 (+ 지도 클릭의 station_id / gu)
 → Supervisor: 주유소 진단 / 자치구 묶음 / 시나리오 / 이름 찾기(같은 이름이면 되묻기)
 → 코드 워커: MCP Tool로 수요·공급·수소·자사 묶음·기준 판정을 병렬 조회 (실패 Tool은 격리)
 → 사실 [F1..Fn] → 분석 에이전트(LLM)가 판별 — 기준 판정 값은 보지 않음
 → 권위 게이트(코드): 기준과 다르면 교정 → 확정 판정 [J], 판단 이력 저장
 → 작성 에이전트: 코드가 만든 답변 뼈대(숫자·[F]·[J])를 문장으로
 → 검증 에이전트: 답변 숫자·인용을 사실과 대조 + LLM-as-Judge, 불합격 시 1회 재작성
 → SSE로 단계와 답변을 화면에
```

상시 작업은 같은 그래프를 작업 이름으로 실행합니다. 1차 감지는 코드가 하고, **변화가 없으면 LLM을 한 번도 부르지 않습니다.**

| 작업 | 1차 감지 (코드) | 변화가 있으면 |
|---|---|---|
| 일간 추적 | 직전 수집에서 정상이던 자사 거점 반경 1km 급속이 그 뒤 3회 수집 연속 고장 — 멈춘 이유(통신이상·점검중·운영중지)별로 알림 | 분석 판별 → 게이트 → 알림 1건 |
| 주유소 주간 추적 | 수집 시점 비교로 자사 거점 1km 안 급속 신설·철거 (운영사·거리) | 정책·경쟁 에이전트 → 게이트 → 보고 1건 |

## 실행

```bash
bash sh/setup_venv.sh          # 처음 한 번 (.venv 생성)
bash sh/run_agent_fake.sh      # 백엔드 :8100 — 결정론 fake LLM, 과금 없음
bash sh/run_frontend.sh        # 대시보드 :8600 (새 터미널)
```

| LLM 백엔드 | 명령 | 비용 |
|---|---|---|
| fake (규칙으로 답함, 시연 안정) | `bash sh/run_agent_fake.sh` | 없음 |
| Ollama (로컬 qwen3:0.6b / 8b) | `bash sh/run_agent_ollma.sh` | 없음 (로컬) |
| OpenAI | `bash sh/run_agent_openai.sh` | **과금** |

fake LLM은 경유 유휴 위험을 일부러 1건 틀리게 판별합니다(감소율 순위를 보지 않음). 그래서 권위 게이트가 교정하는 장면이 매번 재현됩니다.

## 화면

- **지도:** 주유소 470곳을 회사별 8색 핀(색각 이상 고려)으로 보여줍니다. 자사·타사 핀은 같은 크기이고 ⚡는 급속 후보입니다. 자치구는 경계선을 따라 빨강 채움이 충전기 부족, 파란 점선이 경유·LPG차 감소입니다.
- **정보 패널:** 핀·자치구를 누르면 LLM 없이 수 ms 안에 뜹니다. 코드 기준 판정과 이유, 반경 1km 급속·경쟁 운영사, 전환 유형 선택지, 현장 확인 항목, 결정 입력이 있습니다.
- **채팅:** 클릭한 대상이 질문에 채워집니다. 분류 → 조회 → 판별 → 게이트 교정 → 근거 카드 → 검증 단계가 실시간으로 보입니다.
- **알림함:** 일간 추적·주유소 주간 추적 실행 결과를 보여줍니다. 알림의 거점을 누르면 지도에서 해당 핀으로 이동합니다.

## 주요 API

| 경로 | 내용 |
|---|---|
| `GET /chat/stream?message=&station_id=&gu=&company=` | 채팅 (SSE) |
| `GET /api/pins` · `/api/stations/{id}/card` · `/api/districts/{gu}` · `/api/clusters/{gu}` | 지도·패널 (에이전트와 같은 MCP Tool) |
| `GET /api/stations/{id}/simulate?fast_add=` | 충전기 N대 신설 시나리오 (자사 거점만) |
| `POST /api/decisions` · `GET /api/decisions` | 사람의 결정 입력·조회 (에이전트는 읽기만) |
| `POST /api/jobs/{daily_watch\|weekly}/run` · `GET /api/alerts` | 상시 작업 수동 실행·알림함 |

## 테스트와 평가

```bash
.venv/bin/python3 -m pytest -q                              # 실데이터 스냅샷으로 단위·흐름·API 테스트
LANGCHAIN_TRACING_V2=false .venv/bin/python3 eval/run_eval.py fake     # 평가 질문 18개
LANGCHAIN_TRACING_V2=false .venv/bin/python3 eval/run_eval.py ollama   # 로컬 실모델로 같은 평가
```

평가 질문 18개(주유소·자치구·시나리오·이름 찾기·타사·재계획). 정답 숫자는 그래프를 거치지 않고 스냅샷에서 바로 계산했습니다.

| 지표 | fake | Ollama 개선 전 | Ollama 개선 후 | Ollama 우선순위 반영 후 (최신) |
|---|---|---|---|---|
| 답변 숫자 정확도 (근거 없는 숫자) | 100% (321개 중 0) | 100% (281개 중 0) | 100% (297개 중 0) | 100% (300개 중 0) |
| 정답 숫자 포함 | 31/31 | 31/31 | 31/31 | 31/31 |
| LLM 판별 일치율 (게이트 교정 전) | 85.2% (일부러 넣은 오판 포함) | 53.7% (게이트 교정 25건) | 88.9% (게이트 교정 6건) | **85.2%** (게이트 교정 8건) |
| 검증 합격 | 18/18 | 18/18 | 18/18 | 18/18 |
| 요청 분류 | 18/18 | 17/18 | 18/18 | 18/18 |
| 급속 후보 우선순위 AI 채택 · 반복 3회 같은 순서 | 4/4 · 2/2 | - | - | 4/4 · 2/2 |
| 응답 시간 중앙값 | 0.04초 | 68초 | 63초 | 79초 (우선순위 판단 1회 추가) |

Ollama 모델: 분류·답변 판정 qwen3:0.6b, 분석 판별·작성 qwen3:8b. **개선 전→후**에 바꾼 것은 세 가지입니다.

1. 분석 에이전트에게 빠져 있던 사실(25구 중 전기차 증가율 순위·급속 밀도 순위)을 넣었습니다.
2. 순위 읽는 법("1위 = 가장 심함, 상위 20% = 1~5위")을 프롬프트에 명시했습니다.
3. 분석 판별에만 생각 모드를 켰습니다.

기준값(병목 컷, 합산 점수)은 여전히 주지 않습니다. 그래서 일치율은 "같은 데이터를 본 AI가 사람이 정한 기준과 같은 결론에 이르는가"를 재는 신뢰도 지표로 남습니다. 항목별로 확인한 남은 불일치(동작·광진)는 경계 자치구로, AI가 "두 순위가 모두 심해야 병목"으로 보고, 기준은 "순위 합"으로 봅니다. 이런 경우 권위 게이트가 기준으로 확정합니다.

우선순위 반영 후 일치율이 88.9%에서 85.2%로 내려간 것은 동대문구·금천구 묶음에서 1건씩 더 틀린 결과입니다. 분석 입력은 개선 후와 같게 맞춰 두어, 모델의 흔들림인지 원인을 확인 중입니다.

질문별 결과는 [eval/results_fake.md](eval/results_fake.md), [eval/results_ollama.md](eval/results_ollama.md)(최신), 개선 전은 [eval/results_ollama_baseline.md](eval/results_ollama_baseline.md)에 있습니다.

## 하지 않는 것

판매량·재고 기반 유휴 관리, 부지 적합성 판정, 투자 금액·수익 예측, 서울 밖 분석은 하지 않습니다. 근거 데이터가 없기 때문입니다. 대신 차량 감소(유휴 위험)는 **자치구 신호**로, 전력·안전거리는 **현장 확인 항목**으로 사람에게 넘깁니다. 사내 판매량 Tool을 붙이면 같은 엔진으로 거점 단위 판단까지 확장할 수 있습니다.
